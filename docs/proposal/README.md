1. # **Overview (Expected: 1 page)**

**Describe your project at a high level. What is the purpose of this software? What problem does it solve? Use these questions to guide your writing. Remember, we are focusing solely on the main system in this report, without considering the user interface options. When you submit your document, remove the bold instructions. The rest of this section has filler text generated by which is only present to give you a sense of the expected length of the section.**

Brachify is the program BC Cancer Kelowna uses to turn a brachytherapy plan into a cylinder that can be 3D printed for one patient. The treatment is already planned in BrachyVision or Oncentra. Needles are placed so a radiation source can treat the tumour while sparing the organs beside it. The hard step comes after that plan. Those needle paths still have to become a solid cylinder, with a channel for each needle, before anyone prints it and uses it on a patient. Building that shape by hand is slow, and a small error means the printed cylinder does not match the plan.

Brachify reads the DICOM plan, rebuilds the needles, and generates the cylinder around them, with a central channel, an orientation mark, and an optional base. Our work extends that system. The physicist can see the tumour and nearby organs together with the needles, change the cylinder and the needle paths, and start from a saved template when the case fits a design the clinic already uses. The system then writes a file for the printer and a one-page reference sheet that lists each channel.

A typical case runs like this. The physicist exports the plan and structure set from BrachyVision or Oncentra and imports them into Brachify. They turn on the tumour and organs, lower the rectum's opacity, and slice through the area where a needle passes close to it. Brachify flags that needle and shows its distance. The physicist rotates the needle slightly away, confirms that the flag clears and the design still follows the clinic's planning rules, then exports the STL and the reference sheet. The machinist prints the cylinder, and the QA team checks it against the sheet before it is sterilized. For a standard case, the physicist skips the import, opens one of the clinic's locked templates, adjusts the length, and exports it directly. The administrator physicist updates those locked templates when the clinic changes its standards.

Our scope is the step between the finished plan and the printer. This is showing and checking the tumour and organs, editing the cylinder and needles, saving and reusing templates, and making sure every change reaches the STL, STEP, and PDF outputs. Dose calculation and changes to the plan inside BrachyVision or Oncentra are out of scope.

Medical physicists at BC Cancer Kelowna use Brachify after a treatment has already been planned in BrachyVision or Oncentra. They open that plan, review the cylinder, needles, tumour, and nearby organs, then adjust the design or start from a saved template. They export a file for 3D printing and a one-page reference sheet. The machinist prints the cylinder, and the brachytherapy team checks it against that sheet before the patient is treated. One physicist also keeps the clinic’s standard cylinders and needle presets, so the shared designs stay consistent. That physicist is the system administrator, as they decide which cylinder and needle templates the clinic shares, and they update those standards when the team agrees on a change.

	For this project, we are adding to an already existing program (Brachify) which uses Python. Therefore, we are going to be continuing to use this for our entire backend. For our front end, we have looked into different Python frameworks; however, we think that the one being used (PySide6) currently is sufficient. Therefore, we don't have to switch anything. This avoids any confusion for previous developers and contributors.

| Option | Pros | Cons |
| :---- | :---- | :---- |
| Python with PySide6, pythonocc (OpenCASCADE) and pydicom (chosen) | The DICOM import, cylinder geometry and STL/PDF export already work. pydicom is the standard library for DICOM RT files. OpenCASCADE builds exact solids for printing. PySide6 ships as the offline Windows app the clinic already uses. | Slower than C++ for large organ meshes. |
| C++ with Qt, OpenCASCADE and VTK | Fastest rendering. Same geometry libraries. | Rewrites working code in a new language. Harder for the client and future students to maintain. |
| TypeScript | Modern interface, many 3D examples. | Many functionalities that currently work great must be rebuilt. Weak DICOM RT support. Harder to deploy on hospital machines. |

| Testing option | Pros | Cons |
| :---- | :---- | :---- |
| pytest with pytest-qt (chosen) | Short tests and reusable fixtures for sample DICOM plans. pytest-qt clicks through the real PySide6 interface automatically | Adds packages to the environment. It cannot check the rendered 3D image itself. |
| unittest | Built into Python | Wordier and weak fixtures |

We chose the Python stack because it is the only option that keeps Brachify's working, clinically used geometry and still runs offline at the clinic. We chose pytest with pytest-qt because it has the abilit yto automate both milestones (section 3\) such as that backend tests call functions directly, and interface tests drive the real screens.
